# No comments

Project overrides: read `.cursor/fstack/project.md` and `.cursor/fstack/no-comments.md` from the repo root when present; they win over this file.

Agents copy what already exists. A comment that explains a temporary workaround spreads and gets reused as an excuse for more hacks ([poteto](https://x.com/poteto/status/2110149626133438732)). Do not write comments. Make the code say it.

## Default

Do not add comments in JS/TS (`.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`). Leave `*.sh` and other non-JS/TS files untouched. Leave `${var#pattern}`, `${var##pattern}`, and `${#var}` whole — that `#` is a shell parameter expansion, not a comment. Delete the comment you were about to write. Prefer, in this order:

1. A name that states the intent.
2. A small extracted function or block.
3. A type, schema, or assertion.
4. A test that fails when the behavior drifts.

A line that restates the next statement, a section banner, commented-out code, a `HACK` note, and a "temporary workaround" note are all forbidden.

## Allowed

Keep only these. If it is unclear whether a keep applies, delete the comment.

- License or copyright headers required by the file's license.
- Language or tool directives the compiler, bundler, or runtime needs: `"use client"`, `"use server"`, `@jsx`, file-level pragmas.
- Lint or type suppressions with the reason on the same directive: `eslint-disable-next-line <rule> -- <reason>`, `// @ts-expect-error -- <reason>`, `stylelint-disable-next-line <rule> -- <reason>`. `@ts-ignore` and `@ts-nocheck` are not allowed; use `@ts-expect-error` with a reason, or fix the type.
- Formatter or codegen sentinels the tool owns: `prettier-ignore`, `biome-ignore`, `@generated`.
- JSDoc on a **public exported API**, and only when the signature, types, and name are not enough (units, thrown errors, a contract callers cannot see). No JSDoc on internals, components, or hooks that are not the slice public API.
- `TODO` and `FIXME`. Prefer a short actionable note (what to do next) and optionally a link to an issue. Sweep keeps them even when the note is thin. A `HACK` note is not this exception.
- A rare link to an external issue, RFC, or spec for a constraint the code cannot express (browser quirk, vendor bug, protocol). The link is the whole comment. Do not add extra sentences around it.

A surprise in this project's code is not an exception. Rename, extract, type, or test until the behavior is obvious. Do not leave a comment that explains the surprise.

## Workarounds

Do not comment a hack. Fix the cause in this change, or keep the code and track the debt in an issue. A workaround that lands with a justifying comment is unfinished.

## Sweep

When the user asks to sweep comments, or `/no-comments` on a repo, path, or diff.

**Done when:** in-scope files have no comments outside Allowed, behavior is unchanged, skipped trees stayed untouched, and lint, typecheck, tests, and build are green.

1. **Scope.** Use the caller's files or diff. Else the current diff against the base branch (default `main`), including the working tree. A whole-repo sweep uses `config.app` when `.cursor/fstack/config.json` exists, otherwise the frontend package.
2. **Skip.** Do not edit `*.sh` or other non-JS/TS files. Leave `${var#pattern}`, `${var##pattern}`, and `${#var}` whole — that `#` is a shell parameter expansion, not a comment. Do not edit generated or vendor trees: `node_modules`, `vendor`, `dist`, `build`, `coverage`, `.next`, `.nuxt`, `.output`, `.svelte-kit`, minified files, `@generated` / `Code generated by` files, lockfiles, and `.cursor/fstack/artifacts/`. Installed skills under `.agents/` are out of scope.
3. **Delete.** Remove every comment that is not an Allowed keep. Do not delete `TODO` or `FIXME`. Do not rewrite a forbidden comment shorter and keep it. Do not change control flow, values, or public signatures. Encoding a leftover surprise as a name, extract, type, or test is a separate change; list it, do not do it in the sweep.
4. **Workarounds left behind.** If deleting the comment leaves a hack in place, open or cite an issue and name the symbol in the reply. Do not restore the comment.
5. **Verify.** Run lint, typecheck, tests, and build. With fstack config: `checks.onStop`, the app's unit test command, and `verify.build`. Without config: the app's `lint`, typecheck, `test`, and `build` scripts. A red check fails the sweep. Revert the file that broke the check, keep the rest, and say which file.

## Lint

fstack does not ship an ESLint config. If the app already has ESLint, add these (do not add a new plugin to do it):

```js
{
  rules: {
    "no-warning-comments": ["error", { "terms": ["hack", "xxx"], "location": "anywhere" }],
    "@typescript-eslint/ban-ts-comment": [
      "error",
      {
        "ts-expect-error": "allow-with-description",
        "ts-ignore": true,
        "ts-nocheck": true,
        "minimumDescriptionLength": 10,
      },
    ],
  },
}
```

If `@eslint-community/eslint-plugin-eslint-comments` (or `eslint-plugin-eslint-comments`) is already installed, set `eslint-comments/require-description` to `error`. Stylelint: keep `stylelint-disable` reasons; do not add a comments plugin. ESLint cannot fully ban comments with core rules. This skill is the policy; `no-warning-comments` only flags `HACK`/`XXX`, not `TODO`/`FIXME`. `@typescript-eslint/ban-ts-comment` flags suppressions that lack a reason.
