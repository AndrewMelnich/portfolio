# Пайплайн вёрстки целой страницы

`ready-for-agent`

Один шов: процедура страницы (Outer → свежая секция → сборка → implement-spec). Паспорт проекта и ростер моделей — входы этой процедуры, не отдельные фичи.

## Problem Statement

Вёрстка целой страницы по макету занимает часы, потому что агент грилит поведение, которого нет в функциональном описании, ставит implementer на медленную модель, гоняет design-review по кругу на одних и тех же пикселях и заново тянет Figma на каждый проход, открывает интеграционную ветку от окружения dev, а сборку страницы перезапускает, когда в worktree нет локального env.

## Solution

Один проход страницы. Сначала факты из макета и функционального описания, потом grill. Implementer секции работает на быстрой модели и получает указатели, не пересказ. Снимок токенов пишется один раз. Design-review — один проход и максимум один повтор по списку FAIL. Третий промах останавливается на premise. Ветка сборки `front/feature-<page>_page` растёт от `master`. У каждой секции свой MR в эту ветку. Сборка импортирует уже написанный контент секций и верификацию не запускает.

## Implementation Decisions

- Ростер моделей получает роль implementer: `cursor-grok-4.5-high`. Explorer и why-роли остаются как записаны. Родитель страницы подставляет эту роль в каждый implementer Task и не наследует свою модель.
- `master` — главная ветка проекта и ветка прода. Ветки `prod` нет. Ветка сборки `front/feature-<page>_page` от `master`, её MR в `master`. Ветка окружения dev — только URL и деплой. Агент не выводит базу MR из URL стенда.
- Ветка секции: `front/feature-<page>-<section>_section`. MR секции открывается в ветку сборки. Агент MR не мержит. Сборка стартует после того, как эти MR влиты.
- Паспорт фиксирует структуру кадра функционального описания: блоки сверху вниз, каждый блок — изображение или видео, сразу под ним текст функционала. Текст принадлежит медиа над ним.
- Outer, до grill: прочитать секцию страницы в макетах и одноимённый кадр функционального описания этими парами. Сценарий анимации читать, только если пометка или текст пары на него ссылается. Grill свежей секции цитирует текст под её медиа. Поведение, которого в этом тексте нет, в вопросы не попадает.
- Свежий тикет пишет снимок токенов секции до design-review. Потолок ревью живёт в одном месте — протокол родителя design-review. Процедура страницы и завершение figma-to-code ссылаются на этот потолок и не повторяют его другими словами.
- Потолок design-review: первый Task читает снимок, если он есть. Второй Task разрешён один раз, после фикса Critical/Major, и несёт только ещё открытые строки FAIL. Третий FAIL той же секции — premise одной фразой, без нового Task. `INCOMPLETE` и `REFUSE` не являются вторым Task. Родитель не запускает review секции с PASS в её MR.
- Кадр без снимка читается по лестнице, по одному узлу за раз. Сначала project-scoped Framelink. Статус `error` / `needsAuth` / обрыв discovery — user-scoped Framelink. Оба недоступны — прямой REST `GET /v1/files/:key/nodes` с токеном репозитория, затем снимок на диск. Ответ 429 — подождать `Retry-After` и повторить тот же источник один раз. 429 не переключает источник и не запускает новый воркер. Параллельный `get_figma_data` на каждый узел запрещён: один общий токен, user-scoped процесс один на все окна и от залпа перезапускается.
- Code-review один на MR секции, одним сабагентом, модель — explainer ростера. Ветка сборки этот diff не ревьюит. На ветке сборки верификации нет: ни verify-ui, ни layout proof, ни before-shot, ни visual-judge, ни motion probe.
- Контент секции — одна const того же типа, что props секции, лежит рядом с секцией. Разметка секции берёт только props. Вёрстка и верификация рендерят эту const. Сборка импортирует const во view в порядке секций и строки не переписывает. Комментарий `TODO: вынести в page` не ставится: const уже общий источник, перенос на страницу дал бы вторую копию.
- Промпт implementer: путь процедуры, номер тикета, worktree, ветка секции, ветка сборки. Текст контракта секции остаётся в тикете. Чтение тикета — команда CLI трекера `glab`.
- Worktree секции копирует локальный env фронтенда (файл, где лежит публичный хост API) до любого превью. Превью секции не стартует при отсутствии этого файла. Ветка сборки превью не поднимает.
- Обрыв транспорта: resume того же агента секции, первый шаг — статус worktree. Новый агент секции запускается, только если resume недоступен, и останавливается, если MR секции уже открыт.
- Доказательство свежей секции, на её ветке: снимок, design-review в потолке выше, hover и hit target для новых контролов, layout proof, before-shot, visual-judge, motion probe, verify-ui. Всё это рендерит const секции.
- Заметки explore по-прежнему необязательны и лежат вне репозитория. Они не дублируют процедуру.

## Testing Decisions

Хорошая проверка — внешнее поведение прогона страницы: какие факты прочитаны до вопроса, какая модель у implementer, от `master` ли ветка сборки и куда открыт её MR, есть ли MR секции в ветку сборки, сколько design-review Task у секции, один ли code-review на этот MR, жив ли превью секции без локального env, импортирует ли view const секции. Внутренности воркера не проверяются.

Автоматического теста на стеринг-документы в репозитории нет. Проверка этой спеки — прогон шести провалов сессии главной по тексту процедуры. Каждый провал закрыт одним критерием готовности, и два документа не спорят о потолке ревью.

Провалы, которые процедура после правки не пропускает:

- вопрос о поведении секции до чтения её пары «медиа, затем текст»;
- текст функционала, привязанный не к медиа над ним;
- поведение соседней секции, перенесённое на текущую;
- implementer на модели родителя, когда в ростере есть роль implementer;
- ветка сборки не от `master` или её MR не в `master`;
- секция без MR в ветку сборки, или агент влил секцию сам;
- верификация на ветке сборки;
- строки макета, переписанные сборкой или оставленные в разметке под TODO;
- третий design-review Task одной секции;
- повторный design-review родителя после PASS MR секции;
- пиксельный повтор после INCOMPLETE;
- параллельный запрос узла на user-scoped Framelink при живом project-scoped;
- второй code-review на тот же diff;
- превью секции без локального env;
- второй агент секции при уже открытом MR.

Приоритет: уже существующие ворота design-review и premise в ui-mode. Их формулировки приводятся к одному потолку, новый тест-раннер не заводится.
